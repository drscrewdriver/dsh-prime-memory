# L1 决策凭证：幂等键、保留策略与失败隔离

背景：`memory.db` 里每条 L1 记录都是**去重决策的结果**（store / update / merge /
skip），但决策本身不留痕——事后只能看到"结果长这样"，看不到"当时基于什么做的
判断"。判「这次 merge 是否正确」需要**当时的输入快照**，而快照**无法事后补录**。
故凭证必须在整合事件**之前**存在，不能等症状触发。落地为 `l1_receipts` 表
（§B / task_15~18）。

决定：

1. **凭证内容 = 输入指纹 + 结论**。每行记 `run_id` / `record_id` / `kind` /
   `input_digest` / `decided_at`。`input_digest` 是候选池**有序序列**的 sha256
   （`l1-receipts/v1` 前缀 + 逐项长度前缀编码 `${len}:${id}\n`）。三项刻意的
   不可省：**顺序敏感**（`searchCandidates` 返回的是有序候选池，"当时看到哪些
   候选、按什么序"正是要复原的输入；集合语义会丢掉"谁排第一"）、**重复不折叠**
   （候选池里的重复本身是事实，折叠即篡改输入）、**长度前缀**（否则 `['a|b']`
   与 `['a','b']` 会碰撞——序列化不是单射，摘要就失去指纹意义）。

2. **`kind` 五值，`skip_missing` 不得并入 `skip`**。前四值是模型明确给出的动作；
   `skip_missing` 表示**根本没拿到可用决策**（没返回 / 返回非法动作）。合并会让
   回溯失去一半诊断力：「模型决定不存」与「模型没答」是两件事。非法动作一律不
   采信，归 `skip_missing`。

3. **幂等键 = `f(run, record)`，幂等边界是"同一次 run 内同一条记录只留一条"**。
   `receipt_id = inputDigest([runId, recordId])` + `INSERT OR IGNORE`。
   **曾经的设计被实测推翻**：v1 想让 `run_id` = 输入切片的确定性摘要，以获得
   "重跑同一批消息不产生重复凭证"的跨次幂等。但 `pipeline/l1.ts` 对每条抽取结果
   执行 `record_id: newId('mem')`——**模型给的 record_id 被丢弃，记录 id 是运行时
   生成的**。故重跑必然产生新 record_id、必然产生新凭证，跨次幂等**根本不成立**；
   把 run_id 做成切片的函数换不来任何幂等，只会让两次互不相干的执行挤在同一
   run_id 下，反而破坏"一个 run = 一次执行"的归因。改为 `newRunId()`。
   若将来改为沿用模型给的 record_id，跨次幂等可以重新拿到——届时本条需重新评估。

4. **保留策略按 run 数，不按天数**。`RECEIPTS_MAX_RUNS = 1000`。
   理由：本策略要防的是"`memory.db` 无限增长"，而**时间窗口给不出行的上界**——
   阈值与写入速率无关，高频用户 90 天能写进任意多行，无界增长只是被**推迟**。
   run 数上限直接给出上界（`maxRuns × 每 run 条数`）。代价是低频用户历史可能
   变短，可接受：**凭证是诊断设施，诊断要的是"最近发生了什么"，不是考古**。
   量级依据：一轮通常落 5~20 条 → 约 1~2 万行（数 MB）；L1 蒸馏要调一次 LLM，
   每小时至多几次 → 1000 轮约合活跃使用数月。

5. **裁剪粒度是 run，不是行**。task_19 要按 `run_id` 回溯"这一轮蒸馏都判了什么"；
   按行裁剪会切出**半截批次**——少了尾巴的 run 给出**看似完整、实则遗漏**的结论，
   危害**高于查不到**（查不到时用户知道没有数据；半截批次下结论是错的且不可察觉）。
   定序（`MAX(decided_at) DESC, run_id DESC`）只用于决定**保留哪些 run**，删除时
   整批删。`maxRuns <= 0` 或非有限值一律**不裁剪**——"传 0 即清空"太容易被误触。

6. **裁剪挂在 `recordReceipts` 内部，写入之后**。三种挂载点的取舍：交给调用方 →
   未来写路径可能忘记，**"有界"退化为约定**；定时/启动维护任务 → 需要调度宿主，
   插件生命周期内不保证跑到；写在写入路径内部 → **"有界"成为结构性保证**，任何
   写路径都不可能绕过。裁剪排在写入**之后**且包在 try 里：失败最坏是这次没省下
   空间，**绝不因此弄丢刚落盘的凭证**。

7. **红线：裁剪只碰 `l1_receipts`，绝不碰 `l1_records`**。前者是可丢弃的观测数据，
   后者是用户的事实源——为省几 MB 而波及记忆本体，是把容量优化做成了数据丢失。
   由测试用例直接钉住（并做变异探针验证该断言确实有区分力）。

8. **失败隔离：凭证设施永不是主链路的单点**。`persistReceiptsSafely` 只记 warn、
   永不抛出——L1 蒸馏已经把新记忆写进事实源了，此时若凭证写失败还向上抛，等于让
   一个"记录决策"的附属动作把"产生记忆"的主流程打死，代价与收益完全不成比例。
   `recordReceipts` 刻意**不开事务**：凭证单条独立、重放幂等，部分写入无害，
   为它引入事务只会把失败面扩大。

9. **不做配置项（YAGNI）**。保留阈值不做成用户可配：配置要走 schema / 契约 /
   设置页，为一个诊断表的容量引入用户可见面，收益与面积不成比例。真需要调就改
   常量；`recordReceipts(rows, { maxRuns })` 已留出显式注入口。

10. **`record_id` 维度的取值面是 0 或 1 行，不是"判定史"**（task_19 执行期修正的
    一处**说过头**）。查询按两个维度实现（`record_id` / `run_id`，同给为 AND），
    但由条 3 的 `newId('mem')` 决定：**记录 id 每轮新铸、从不复用**，故一个
    `record_id` 只可能属于一轮 run。端到端实证（真管线两轮 → 真端点）见
    `evidence/task19-backtracking-raw.json`：run 维度 2 / 1 行，record 维度 **1 行**。
    该维度正确回答的是「**这条记忆出自哪一轮、当时看到什么候选池、被判成了什么**」，
    **不是**「它历次被怎么改过」。查询层仍按可多行实现——将来若复用 id 或沿用
    模型给的 id，此处无需改动；但对外措辞必须与现状一致。

组合关系：条 3 的幂等与条 6 的失败隔离正交——前者保证"不重复"，后者保证"不阻断"。
条 4/5 是本表自身的容量治理，与 §C 的记忆冻结、§G 的图谱可重建性无关：凭证链是
**只读旁证**，不参与任何重建路径，删掉全部凭证不影响 L0→L1→图谱 的任何一步。
