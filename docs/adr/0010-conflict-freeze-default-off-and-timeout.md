# 矛盾冻结：默认关闭、安全阀与裁决出口

背景：L1 去重的**决策词表**只有 `store` / `update` / `merge` / `skip`——我们的
"冲突检测器"（`CONFLICT_DETECTION_SYSTEM_PROMPT`）检测到矛盾后，**由 LLM 直接裁决落盘**：
`update` 覆盖或 `merge` 合并，**没有"停下来等人裁决"这个选项**。命名与能力的落差
（函数叫"冲突检测"，却没有任何冲突处置动作）本身就是缺口的旁证。

对标 mneme 的 dream layer，本方案继承两条设计要点：**opt-in** 与
**不自动裁决**（原话：*"the dream layer does **NOT** auto-adjudicate winner/loser —
the conflicting pair is parked here until a human reviews it."*）。

落地为 `conflict_pending` 表 + `conflict` 动作 + `conflictFreeze` 配置 + 裁决工具/端点
（§C / task_20~26）。变更面：`prompts/l1-dedup.ts`、`pipeline/l1.ts`、`store/conflicts.ts`、
`store/graph-store.ts`、`store/sqlite.ts`、`tools/index.ts`、`stats.ts`、`config.ts`。

决定：

1. **默认关闭，且零漂移是构造性的，不是比对出来的**。`conflictFreeze.enabled = false`。
   关闭时 `getConflictDetectionSystemPrompt` **直接 `return base`**，而 `base` 就是三份
   已发布常量本身——"关闭态 prompt 与改动前逐字一致"因此是**构造**出来的，不依赖人工复核 diff。
   为此**刻意不把三份 base 常量改成函数**：改成函数会重排大段文本，让零漂移无法用逐字比对
   表达，只能退化为"看起来一样"。开启态才做一次定点替换（action 枚举行）+ 追加条款。
   理由：冻结消耗**人的注意力**，不可默认全开。

2. **冻结不是"拦住写入"，而是"不自动裁决"**。新记忆**照常入 L1**（与既有 `store` 路径
   复用同一个 `toStoreRecord`，逐字段一致），与冲突的旧记忆作为**一对**停放到
   `conflict_pending`，**双方内容都不被改写、不被删除、不被合并**。
   判据是可观测的：新记录的 `version === 0`（store 语义）而非 `1`（merge/update 语义）。
   若实现成"拦住写入"，代价是**丢信息**——那比它想解决的"自动裁决"更糟。

3. **`conflict` 的不合法输出回落 `store`，绝不落到 update/merge 兜底分支**。
   `pipeline/l1.ts` 的应用循环只对 `store`/`skip` 显式分支，**其余动作一律落到 update/merge
   分支**。执行期实测：conflict 决策按设计不带 `target_ids`，于是 `targets=[]` → 记录被当成
   "替换了 0 条"的合并产物追加，`version` 被算成 **1**——**不报错、不丢数据，唯一痕迹是一个
   version 数字**。一个显式声明了"拿不准"的决策，绝不能被静默解读为"新记忆更优"去覆盖旧记忆。
   校验不过（winner 非空 / 二者不同 / 恰有一方是本条新记忆且对侧在候选池内）或开关关闭时，
   一律回落 `store`。

4. **`winner` / `loser` 二者必须不同，且只表示"排序位"，不代表结论**。承自 mneme 的
   `validateDecisions`。取值来自「本条新记忆的 `record_id`」∪「候选池中的 `record_id`」。
   promise 的语义边界必须说清：winner 只用于确定"进入待裁决对时谁在前"，
   **最终结论落在 `resolution` 列**。

5. **安全阀的语义是"不收新的"，不是"偷偷删旧的"**。两轴：`maxPending`（默认 100）——
   未裁决数达上限时新的冲突**不再停放**，当场按 LLM 的 winner/loser 了结；
   `timeoutDays`（默认 30，**0 = 显式关闭超时降级**，不是"立刻全部超时"）——
   停放超时的对在下一轮蒸馏开头被了结。
   关键约束：**被自动了结的对仍写进 `conflict_pending`**，只是 `resolved_at` 非空。
   有界性由"不收新的"给出，而不是靠删除用户还没看过的裁决请求——后者是**丢工作**而非省空间。
   没有安全阀的两个后果都是确定的：队列无界增长；一条永远没人看的待裁决对会让
   "两条互相矛盾的记忆长期并列召回"**永久**留在库里，比它想解决的问题更糟。

6. **自动了结必须与人工结论在审计上可辨认**：`resolution` 取值
   `winner` / `loser` / `both`（人工）+ **`auto`**（安全阀）。若自动了结在人眼里与人工结论
   无从区分，§C 最想消灭的"机器替人裁决"会以**悄悄发生**的形式回来。
   本条的准确性完全依赖 §B 凭证链——故 §C 必须有 §B 才能成立。

7. **"回落现有 LLM 自动裁决"= 按 LLM 当时已给出的 winner/loser 了结，不重新调用 LLM**。
   停放时 LLM 已经给出过 winner/loser；重新提问既浪费一次调用，也**不可能**提供第一次调用
   所没有的信息。原计划措辞的准确含义是"§C 之前那种机器决定、无人复核的行为"，
   而非"再问一次模型"。

8. **有冻结就必须有裁决出口，否则冻结不成立**。`memory_resolve_conflict` 工具 +
   `dsh-memory/conflict-resolve` 端点（共用 `src/conflict-service.ts` 同一形状与语义）。
   否则队列是**只进不出的黑洞**，安全阀的自动了结会成为唯一出路——那等于把 opt-in 的冻结
   悄悄退回成"超时后机器自己判"。顺序刻意为之：**先打 `resolved_at` 再退场 loser**；
   反过来的话，"记录已消失、队列里那条仍在待裁决"这种状态要等人再点一次才发现无据可依。
   打标用 `WHERE resolved_at = ''` → **二次裁决不覆盖第一次结论**（裁决是一次性判定行为，
   自动了结与人工裁决的次序因此不可逆）。

9. **`resolved_at` 用空串而非 NULL 表示"未裁决"**，与 `l1_receipts` 的 `''` 约定一致，
   避免 `= ''` 与 `IS NULL` 两套判据并存。未裁决索引建为**偏索引**
   （`ON conflict_pending(created_at) WHERE resolved_at = ''`）——队列上限与裁决工具
   **只关心未裁决行**，该索引同时覆盖 `created_at` 排序（上限取最旧、超时扫描亦然）。

10. **图谱 `disputed` 是派生同步，不是单向标记**。`GraphStore.syncDisputed(冲突集)`：
    `active` 且来源命中 → `disputed`；`disputed` 且来源不再命中 → 复原 `active`；
    `archived` 墓碑两边不动。管线侧传的是**当前全部未裁决对的记录集**，而非本轮新增那一对。
    理由：图谱是本仓库反复确认的 **L1 派生投影**，派生字段必须**由当前事实重算**——
    裁决会**撤销**争议，单向标记会让已裁决的节点永远停在 `disputed`，那是**派生投影在说谎**。
    （`disputed` 在 `graph/search.ts` 仍进检索候选，是"照常召回、但状态可见"的中间态。）

11. **扩动作词表必须同步检查所有消费该词表的地方**。执行期实测：`normalizeKind`
    的白名单停在四个旧动作，§C 新增的 `conflict` 未登记，于是 §B 凭证把"模型**明确**说
    判不了"记成 `skip_missing`（= "模型**没答**"）。§C 的裁决可审计性**完全**依赖 §B，
    记错比缺一条更糟：缺了是"查不到"，错了是"**查到了错的**"。已修并补端到端断言。
    判据：扩词表时要同步检查凭证归一、统计日志、渲染文案、schema 描述——
    跨波次的词表扩展天然落在两波测试的交界缝隙里。

12. **未定档项（如实标注）**：`maxPending = 100` / `timeoutDays = 30` 的定档依据是
    **设计推演，非容量实测**（与 ADR-0006 条 4 的 `RECEIPTS_MAX_RUNS` 同款情形）。
    推演依据：100 条待裁决 ≈ 连续 5~20 轮蒸馏全在冲突，远超正常使用强度，真达到说明
    该调 prompt 而不是加容量；30 天足够跨过假期与项目间歇，又不至于让互相矛盾的两条记忆
    长期并列召回。若将来实测显示不合适，属**参数调整，非设计返工**。

组合关系：

- 条 1 的零漂移与条 5 的安全阀正交——前者保证"不开启就没有任何行为变化"，
  后者保证"开启了也不会无界增长"。
- 条 2 的"不覆盖"与条 8 的"可裁决"构成完整闭环：**冻结期间谁的账都不动，
  人的结论才动账**。
- 条 10 的图谱同步与条 8 的裁决是同一件事的两面：裁决一旦生效，图谱必须能**撤销**争议，
  否则派生投影与事实长期不符。
- 与 ADR-0006 的关系：§B 是 §C 的**审计前提**（条 6、条 11），但两者相互独立——
  关掉 §C 不影响 §B；删掉全部凭证不影响冻结与裁决的执行，只是事后无法审计。
- 与 §E（存储作用域）、§F（图谱向量列）无关：本 ADR 的全部结论都在 L1 去重与图谱状态
  两层之内，不改变数据目录布局，也不改变图谱的存储形态。
