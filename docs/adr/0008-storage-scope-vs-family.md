# 存储作用域与 family 的正交划分

> **状态：已落地**（2026-09-16，提交 `efb0f42`，Wave 3；CI 七步链全绿）。
> 本 ADR 正文的五条决策**一条未改**——实现是按它做的，不是反过来迁就实现。
> 落地记录（新增事实，不改决策）：
>
> - **触发方式**：按**显式例外**启动，不按症状启动。症状条件（"确实跨工作区使用且
>   `work` 族互相污染"）**字面不成立**；启动依据是用户显式指令。之所以可接受，
>   是 §E 与 §B/§G 的"不可追溯性"**性质相反**：`scope` 不改写既有记忆内容，
>   晚做只产生"隔离生效前写入的 work 记忆混在全局根"，可由迁移一次性归位。
> - **存储形态取"单根 + 归属列"**（条 5 明说这是实现细节，ADR 不预绑）：
>   `l1_records` / `l1_fts` 各加 `scope` + `workspace_id` 两列。
> - **哪些还没做**（条 1「四象限都存在」的现状）：四象限的**语义与判定**已落地并可测，
>   但**记录级显式覆盖无产品写入入口**——`resolveRecordScope` 的 `explicit` 参数
>   目前只有测试调用方。默认规则两条（work→workspace / chat→global）已在全部写入路径生效。
> - **本条前置的交叉检查项已兑现**：`scope` 过滤落在与族隔离**同一层**
>   （`searchL1Fts` / `searchL1Vector` / `searchCandidates` / `graphLane`），
>   不是只在检索出口过滤。
> - **§C 侧仍未兑现**：待裁决队列查询**目前仍不带作用域维度**（见下方组合关系末条），
>   已在 checklist 开放项登记。
> - **工作区标识取什么**——本 ADR 未涉及，由 ADR-0009 单独钉住（结论是 canonical cwd，
>   而非宿主 `dsh-workspace` 的 `WorkspaceId` uuid）。

> 原文（写入时，保留以免丢失当时的判断依据）：
> 本 ADR 记录的是**设计决策**，不是已交付的能力。落地属 Wave 3（§E），
> 触发类型为**症状**（条件：确实跨工作区使用，且 `work` 族记忆互相污染）。
> 截至本 ADR 写入时，`scope` 配置**不存在**，README 与设置页**均未提及**——
> 文档不得描述未实现的能力（该半项已在收口检查清单里改判为 Wave 3 的交付项）。

背景：`config.ts` 的 `resolveDataDir` 解析到 `dshHomePath('memory')`，即**单一全局根**，
没有任何作用域控制。这意味着**所有项目共用一份记忆库**：在项目 A 里沉淀的 `work` 族记忆，
在项目 B 的会话里同样会被召回。

今天的记忆系统已经有**一个**划分轴，但它回答的不是这个问题：

| 轴 | 含义 | 解决的问题 | 现状 |
|----|------|-----------|------|
| `family` | **内容类型**（chat / work） | 个人记忆与团队工作记忆不要混在一起 | ✅ 完整 |
| `scope` | **可见范围**（global / workspace） | 同一类型的内容该在多大范围内可见 | ❌ 缺失 |

决定：

1. **`scope` 与 `family` 正交：互不替代、互不推导**。两条轴回答两个不同的问题——
   `family` 问"这是什么内容"，`scope` 问"它该在多大范围内可见"。
   **严禁**让一条轴退化出另一条，例如"`work` 族一律是 workspace 的"或
   "`chat` 族一律是 global 的"作为**默认推导**。正交的含义是四象限都存在：
   `chat×global`（个人偏好）、`chat×workspace`（本项目的个人笔记习惯）、
   `work×global`（跨项目通用的团队 SOP）、`work×workspace`（本项目的任务与状态）。
   把两条轴合并成一条，等于把一个二维决策压成一维偏好，日后任何一格需要例外时都会返工。

2. **`workspace` 模式下按工作区隔离 `work` 族；`chat` 族**默认**仍全局**。
   理由：个人记忆本就应当跨项目（"用户偏好简洁回答"不属于任何项目），
   而团队工作记忆的污染面恰恰在项目之间。
   **注意这不与条 1 冲突**：这是**默认值**，不是推导规则——`chat×workspace` 仍是合法取值，
   只是不作为默认。

3. **向后兼容是硬要求：既有单根数据默认归 `global`，迁移不丢失、不删除**。
   存量用户的全部记忆都已存在，任何"迁移"都必须是**标注归属**而非"搬运/重建"——
   把用户数据搬来搬去是拿事实源冒险去换一个配置项的美观。

4. **`scope` 解析失败走既有降级路径，不抛错、不阻断启动**。与本仓库其他配置项同一原则：
   一个可见范围配置读错，绝不该让插件树加载失败（历史上 `nullable` 崩溃整棵插件树的
   教训见 `ENGINEERING-NOTES.md`）。非法值按 `global` 处理并告警一次。

5. **本决策不改变数据目录布局的既有语义**。`resolveDataDir` 的现有行为是**基线**；
   `scope` 是在其之上叠加的**过滤维度**。是否按工作区分目录、还是单根 + 归属列，
   属实现细节——**本 ADR 只钉住"归属必须可判定、且既有数据判为 global"**，
   不预先绑定存储形态（这也是它能在未实现时就先定下来的原因：钉住的是语义，不是表结构）。

组合关系：

- 与 `family` 的关系：正交（条 1）。`family` 的族隔离在**去重候选召回**上已经生效
  （"去重永不跨族"）；`scope` 若落地，其过滤必须落在**与族隔离同一层**，
  不能只在检索出口过滤而让去重候选跨工作区相互污染——那会生产出"看不见但已经影响了
  决策"的记忆，比不隔离更糟。
- 与 §A（子代理档位隔离）的关系：§A 解决的是**同一会话树内**的可见性（档位沿父链继承）；
  `scope` 解决的是**同一档位下跨工作区**的可见性。两者是不同维度，都不可互相替代。
- 与 §B（决策凭证链）的关系：凭证表记录的是"这一轮判了什么"，**不带 scope**；
  若将来凭证需要在跨工作区场景下区分归属，必须在**写入时**就带上——
  与本仓库"凭证必须在事件之前存在"的结论同理（ADR-0006 条 3 的教训：
  属性无法事后补录）。
- 与 §C（矛盾冻结）的关系：待裁决队列**必须**尊重 `scope`——一条在项目 A 冻结的冲突对，
  不应在项目 B 的会话里被展示或裁决。**这是 §E 落地时必须回头检查的一处**：
  §C 先于 §E 实现，其队列查询目前不带作用域维度。
