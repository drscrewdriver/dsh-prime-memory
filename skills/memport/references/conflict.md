# MemPort 冲突判定与裁决

原则:**宁可并存,不可静默覆盖**。记忆库里两条相关记忆的代价远小于丢掉一条唯一真相。

---

## 1. 三层判定

| 层 | 手段 | 输出 | 谁做 |
| --- | --- | --- | --- |
| L1 精确层 | 归一化内容哈希(sha256 前 16 位) | `dup` | `memport.py plan`(确定性) |
| L2 相似层 | 综合相似度 = `max(3-gram Jaccard, 2-gram Dice)`:≥0.62 `near-dup`;0.30~0.62 `conflict-candidate`(阈值经真实语料标定:中文改写对 0.49~0.51,无关对 0.16~0.28) | 候选集 + 分数 | `memport.py plan`(确定性) |
| L3 语义层 | 判"互补还是矛盾",定四选一 | `final_verdict` / `cf` / `rw` | Agent(LLM) |

确定性层只负责**把候选缩到 1~3 条**,不做结论。语义层只看候选,不看全库。

## 2. 判定的四个维度

对每条候选,按顺序比:

1. **主体**:说的是不是同一个对象?(项目/人/文件/命令/概念)。主体不同 → 不冲突,各留。
2. **有效期**:`vf`/`vt` 区间是否重叠?**比的是有效期,不是 `created`**——两条记录入库时间谁新,跟谁的事实更新无关。两边都是 `?`(未判定)时退化为比 `updated`。
3. **取值**:同一主体的属性值是否相容?(版本号、路径、阈值、结论)
4. **极性**:是否一方是另一方的否定/反转?("用 A" vs "不要用 A")

只有 1 同、且 3 不相容或 4 相反,才是**真冲突**。

### 持续性决定"能不能被取代"

| `st` | 能否被后来者取代 | 理由 |
| --- | --- | --- |
| `o` 仍在持续 | ✅ 只有它能 | "现在的状态"会变,新事实可以闭合它的 `vt` |
| `p` 时点 / `s` 已结束区间 | ❌ 永不 | 历史事实的 `vt` 是它自带的,后来者无权改写 |
| `t` 无时间性 | ❌ 永不 | 恒真,不存在"被更新" |
| `?` 未判定 | ⚠️ 交用户 | 不知道会不会变,不自动判取代 |

**踩坑示例**:库里有一条 `p`(2026-09-01 完成了 X),导入的新条目说"X 还没做"。这不是"新条取代旧条",而是**两条各自陈述不同时点的事实**,或其中一条本身错了——判 `conflict` 交用户,不要静默 supersede。

## 3. 裁决矩阵

| 情形 | `final_verdict` | `cf` | `rw` | 动作 |
| --- | --- | --- | --- | --- |
| 内容等价(同义改写、措辞不同、事实相同) | `dup` | 0 | 0 | 跳过,不写(但若 `vf`/`vt`/`st` 不同 → 见下行) |
| 内容相同、但有效期或持续性更精确 | `merge` | 0 | 0 | **更新有效期**:改写这条记录的 `vf`/`vt`/`st`,内容不动 |
| 主题相关、信息互补、无矛盾 | `merge` | 0 | 1 | 合成一条更完整的记录写入;旧条**默认保留**并标 `rw=1`,删旧需用户确认 |
| 主体同、取值矛盾、旧条 `st=o`、新条有效期更晚 | `supersede` | 0 | 1 | 写新条(`rw=0`);旧条**闭合 `valid_to`** 并标 `rw=1`(默认只标注不删除) |
| 主体同、取值矛盾、旧条 `st=p`/`s`/`t` | `conflict` | 1 | 0 | 两条并存(历史/恒真事实不可被取代),交用户 |
| 主体同、取值矛盾、时间不可比或旧条更新 | `conflict` | 1 | 0 | 两条并存:新条 `cf=1`,进待裁决队列 |
| 主体不同(仅字面相似,如两个项目同名模块) | `new` | 0 | 0 | 直接写入 |
| 新条是对旧条的部分细化(旧条仍正确) | `merge` | 0 | 0 | 写新条;旧条不动 |

**旧条更新的情况不要"以旧覆新"**:导入的是外部旧记忆,库里的是更新的认知 → 判 `conflict` 并交用户,不写不删。

## 4. 语义裁决提示词(Agent 用)

对 `pending.jsonl` 中每一条(建议按主体分组,一次 ≤ 20 组):

```
判定新记忆与现存记忆的关系。只输出 JSON,不要解释。

新记忆(N):
  类型:{type} · 持续性:{st}(p时点/s已结束区间/o仍在持续/t无时间性/?未判定)
  · 记录时间:{created} · 变更时间:{updated} · 有效期:{vf} ~ {vt}
  内容:{content}

现存记忆(M1..Mn):
  [{id}] 类型:{type} · 持续性:{st} · 变更时间:{updated} · 有效期:{vf} ~ {vt}
  内容:{content}
  ...

判定规则:
- 同一事实的等价表述 → dup
- 内容相同但 N 的有效期/持续性更精确 → merge(内容不动,只更新时间字段)
- 主题相关且信息互补、彼此不矛盾 → merge
- 同一主体、取值相矛盾、且 M 的持续性为 o(仍在持续)、N 的有效期更晚 → supersede
- 同一主体、取值相矛盾、但 M 的持续性为 p/s/t(历史/恒真) → conflict(M 不可被取代)
- 同一主体、取值相矛盾、但时间不可比或 M 更新 → conflict
- 主体不同(仅字面相似)→ new
- 无法确定时一律 conflict,不要猜

输出:{"seq":<序号>,"final_verdict":"dup|merge|supersede|conflict|new",
      "cf":0|1,"rw":0|1,"target":"<被关联的 M id 或空>","merged":"<merge 时的合并正文或空>",
      "close_valid_to":"<supersede 时给旧条闭合的 ISO 时间,或空>","why":"<≤30字依据>"}
```

约束:
- `merge` 必须给出 `merged` 正文,且**不丢失任一侧的独有信息**;合并后仍遵守 ≤100 字书写规范。
- `supersede` 必须给出 `close_valid_to`(旧条停止成立的时间,通常是新条的 `vf`)。
- `conflict` 必须给出 `why`(用户要靠它拍板)。
- 输出 JSON 逐行追加回 `plan.jsonl` 对应行(可用脚本或手工改)。

## 5. `cf` / `rw` 的语义与去向

| 字段 | 含义 | 落库位置 |
| --- | --- | --- |
| `cf`(是否冲突) | 1 = 与库内既有记忆矛盾且**未裁决**;0 = 无冲突或已裁决 | `metadata.memport.cf` |
| `rw`(是否被改写) | 1 = 本条已被后续条目取代/改写(原文保留但失效);0 = 现行有效 | `metadata.memport.rw` |
| `valid_to`(有效期止) | 被取代的 `o` 类记忆应**闭合**此处,而不是删掉它 | 顶层 `validTo` + `metadata.temporal.vt` |

**用闭合有效期代替删除**:一条"目前在做 X"的记忆被"已改为做 Y"取代时,正确做法是把旧条的 `valid_to` 设为切换时刻(它从此是**历史事实**,不再是错的),而不是删掉。这正是时间定位的价值——删除会丢掉"当时确实如此"的信息。

- 导出侧带进来的 `cf`/`rw` 只是**提示**(记进 `cfHint`/`rwHint`);导入侧重新判定后的值才是权威值。
- `cf=1` 的记录仍需**正常入库**(它本身是有效记忆,只是存在争议),同时进待裁决队列。
- 处理完用户裁决后,把结果回写:`cf` 改 0,若判定为被取代则旧条 `rw` 改 1 —— 这一步需要更新既有记录,当前插件**没有 update 工具**,因此:
  - 优先:随插件批量导入工具(通道 C)一并提供 update 能力;
  - 否则:把裁决结果落在 `plan.jsonl` 侧车与报告中,等下次实现。

## 6. 边界情形

| 情形 | 处理 |
| --- | --- |
| 同义改写但长短差异大 | 保留信息更全的一条(`merge`),不要两条都留 |
| 一条是老版本事实(如"v0.9 无 X"),一条是新版本 | **不算冲突**:各自都带版本限定 → 都保留,各加 `tags.key` 区分 |
| 全局规则 vs 项目特例 | 不冲突,项目特例优先作用域更小;两条都留,项目条加 `scope` |
| 用户手工写入的记忆(`scene_name='__manual__'`) | **优先级最高**:任何情况下不删不改,冲突一律判 `conflict` 交用户 |
| 一条与库中多条都相关 | 只对相似度最高的 1~3 条判;结论取最严(`conflict` > `supersede` > `merge` > `new`) |
| 基线快照来自 `records/*.jsonl` 降级路径 | 可能包含已被删除的历史行 → 判 `dup` 前用 `memory_search` 复核该条是否仍可检索 |

## 7. 待裁决队列

导入结束后,未决冲突必须以清单形式交给用户,每条给足信息:

```
[冲突 3/7] 主体:dsh locale
  新(导入) 2026-09-01 work_fact · mp_9f2c1ab7
    官方 DSH LOCALE_IDS 只有 zh/en,ja/ko 无法选中
  旧(库内) 2026-08-20 work_fact · mem-abc123
    官方 DSH LocaleRuntime 支持 zh/en/ja/ko 四语
  判定依据:主体同,取值矛盾,旧条时间更早但结论更宽
  建议:保留旧条为准(更新时间更近) → 新条标 rw=1,或两条并存
```

用户拍板后,把结论落进 `plan.jsonl` 与最终报告;**没有用户确认,不执行任何删除**。
